# Plan: AWS inquiry storage + admin page

**Status:** steps 1 to 4 done (setup guide, API, public form, admin page in `src/admin/`). Step 5 (end-to-end check on the development preview) waits on the accounts in `docs/aws-setup.md`.
This replaces the "simple setup" (Formspree + SharePoint) at the top of
`docs/backend-requirements.md`. Where the two disagree, this file wins.

## Goal

1. A visitor submits the public form **with their bills attached**
   (PDF, JPEG, PNG only).
2. The inquiry is stored in **DynamoDB**; the files go to a **private S3 bucket**.
3. Staff review inquiries in a new **`/admin`** page in this repo: an
   **Inquiries** sidebar, a list, and a detail view that previews each document
   and offers a **Download** button.

## Decisions (made by the business)

| Topic | Decision |
|---|---|
| Admin login | **Microsoft sign-in**, only accounts in the company's own Microsoft 365 tenant (domain `murilloconsulting.co`). Turn on **"Assignment required"** in Entra so only explicitly added users (e.g. Larry) can sign in. |
| Retention | **90 days** for files and inquiry records, deleted automatically |
| Bot protection | **Cloudflare Turnstile** on the public form, verified server-side before any upload slot is issued |
| Extras in v1 | **Email Larry on each new inquiry** (AWS SES), **status labels** (New / Contacted / Closed), **Delete button** |
| AWS region | `us-east-1` unless the user says otherwise |

Note: this reverses the earlier "two-step" decision (contact form first, upload
link later). Public anonymous upload is back on purpose, which is why
Turnstile and the server-side file-content check are required, not optional.

## Architecture

```
PUBLIC FORM
  1. Visitor fills out the form, picks files, passes Turnstile
  2. POST /api/inquiries
       - verify Turnstile
       - validate fields (reuse src/lib/leadSchema.ts with the `en` dictionary)
       - validate file metadata: type allow-list, <= 10 MB each, <= 6 files
       - save inquiry to DynamoDB with status "uploading"
       - return one S3 presigned POST per file
         (content-length-range + Content-Type bound in the policy, ~5 min expiry,
          object key generated by the server)
  3. Browser uploads each file DIRECTLY to S3, with progress
  4. POST /api/inquiries/:id/complete
       - read the first bytes of each object from S3, check magic bytes
         (%PDF / FF D8 FF / 89 50 4E 47 0D 0A 1A 0A) and actual size
       - delete any object that fails; mark the inquiry "new"
       - email Larry via SES: business name + admin link, NO bill data

ADMIN (/admin)
  Microsoft sign-in -> our own signed, httpOnly session cookie (few hours)
  Inquiries sidebar -> list (newest first, filter by status) -> detail
  Documents: 5-minute presigned GET links. Images in <img>, PDFs in the
  browser's built-in viewer (<iframe>), Download uses a presigned GET with
  Content-Disposition: attachment.
```

**Why files go browser -> S3 directly:** Vercel functions reject request
bodies over **4.5 MB**. Bills cannot be proxied through `/api`.

**Why documents render from the S3 domain:** a malicious PDF then runs on S3's
origin, not ours, and cannot reach the admin session cookie.

## API (Vercel functions in `/api`)

| Endpoint | Access | Purpose |
|---|---|---|
| `POST /api/inquiries` | Public + Turnstile | Validate, save, return upload slots |
| `POST /api/inquiries/:id/complete` | Public | Verify files, mark New, email Larry |
| `GET /api/admin/auth/login` | Anyone | Redirect to Microsoft (OIDC code flow, state + PKCE in a short-lived cookie). `?returnTo=/admin/...` is honored only for paths inside `/admin` |
| `GET /api/admin/auth/callback` | Microsoft | Exchange code, verify ID token (issuer, audience, `tid` == our tenant), set session cookie |
| `POST /api/admin/auth/logout` | Admin | Clear session |
| `GET /api/admin/auth/me` | Admin | Signed-in user, or 401. The admin page's sign-in gate |
| `GET /api/admin/inquiries` | Admin | List, newest first, `?status=` filter |
| `GET /api/admin/inquiries/:id` | Admin | Details + presigned view/download URLs |
| `PATCH /api/admin/inquiries/:id` | Admin | Change status |
| `DELETE /api/admin/inquiries/:id` | Admin | Delete S3 objects + DynamoDB item |

## AWS resources

| Resource | Configuration | Cost |
|---|---|---|
| DynamoDB `inquiries` | Encrypted by default. TTL attribute = createdAt + 90 days. Provisioned low capacity to stay in the always-free allowance | ~free |
| S3 bucket | Block Public Access on, default encryption, bucket policy denying non-TLS, CORS allowing POST only from the site origins, lifecycle rule expiring objects after 90 days | cents/month |
| IAM user for the app | Policy limited to that one table and that one bucket (PutItem/GetItem/Query/UpdateItem/DeleteItem; PutObject/GetObject/DeleteObject). Keys only in Vercel env vars | free |
| SES | Verify domain `murilloconsulting.co` (DKIM CNAMEs, separate from the M365 records). Sandbox mode is enough because it only emails Larry's verified address | ~free |

AWS changed its free tier for new accounts in 2025; the user should confirm
current terms when creating the account.

TTL and lifecycle deletions can each lag by a day or two and are not
synchronized, so the admin UI must handle "file expired" gracefully.

## Security checklist

- Every check repeated server-side; browser checks are UX only.
- Server generates S3 keys (`inquiries/<id>/<uuid>.<ext>`); the uploaded
  filename is a display label only.
- Upload slots expire in ~5 min and bind type + max size.
- Post-upload magic-byte check; failures deleted.
- Admin endpoints all require a valid session; session cookie is httpOnly,
  Secure, SameSite=Lax, signed, short-lived.
- No PII or filenames in logs or analytics (see `src/lib/analytics.ts`).
- Deletion is automatic (TTL + lifecycle) plus manual Delete.
